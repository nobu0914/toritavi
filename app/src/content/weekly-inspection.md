## 週次検査（Fable）

**Fable は検査だけ。実行と修正は Opus。** 毎週 1 回、下の指示ブロックを 1 つ
貼る。レーン 1〜6 を Fable が順に回す。

### なぜこの軸か

**「バグ」より「静かな不一致」で痛い目に遭ってきた。** 一般的なコードレビューの
軸をそのまま渡すと、既に 800 件超のテストが守っている範囲を再走査して終わる。
だから軸は**テストが構造的に見られない所**へ寄せてある。

**過去の外部監査は 9 件中そのまま正しかったのが 3 件だった。** 出力は「所見」で
あって「事実」ではない前提で、**検証しやすい形を強制する**のがこの手順の肝。
とくに所見 1 件ごとの「これが偽である条件」を必ず書かせること。これが無いと
Opus 側の検証コストが跳ね上がる。

### 回し方（Fable をどこで動かすか）

**A. Opus に「週次検査を回して」と言う（普段はこちら）**

Opus が下の指示文を Fable 5 のサブエージェントへ渡し、返ってきた所見を
そのまま受け取って真偽判定 → 修正まで一続きでやる。**コピペが要らない。**
レーンごとに別のサブエージェントへ振れるので、1 セッションに全部を詰め込む
必要もない。

独立性は保たれる。サブエージェントは**まっさらな文脈で指示文だけを受け取る**
ので、Opus の思い込みを引き継がない。

**B. 別セッションで自分で回す（出先・別マシン）**

1. **`~/Dev/toritavi_app` を作業ディレクトリにして新しいセッションを開く**
2. モデルを **Fable 5** に切り替える（アプリのモデル選択から）
3. 管理画面 `/admin/maintenance` →「週次検査」タブ → 下のブロックをコピーして貼る
4. 出た所見を Opus のセッションへ貼る

> 🔴 **claude.ai のチャットに貼っても動かない。** コードを読む必要があるので、
> **リポジトリを作業ディレクトリにした Claude Code のセッション**であること。
> ここを外すと、読めないまま「それらしい所見」が返ってくる——監査としては
> 最悪の壊れ方をする。

   「DB 側の確認が必要」と書く。
5. 推測を事実として書かない。推測なら「推測」と明記する。
6. 既存テストが既に守っている事柄を所見にしない。

  高   = 機能が黙って消えている、正本と実装の食い違いで利用者が騙される

  低   = 表記ゆれ、読みにくさ

━━━━━━━━━━ レーン 1: 沈黙（出ないのに落ちない）━━━━━━━━━━

機能が消えても例外が出ない形。呼び出し側は実行したつもりで、画面には何も
起きず、テストも通る。このリポジトリで最も見つけにくく、最も痛い。

実際に起きたもの（校正用。同じ形が他にないか探す）:
- 削除の Undo トーストが 8 箇所すべて出ていなかった
  → Overlay.maybeOf が null を返し、黙って return していた
- 7 か国の入国要件が丸ごと無効
  → applies_to が空＝フェイルクローズで対象外扱いになっていた
- OCR 上限が毎日 9 時間効いていなかった
  → 複製した SQL 関数に、既知の JST 修正が入っていなかった

見る観点:
1. 早期 return・空 catch・?? のフォールバック・orElse・maybeOf・
   フェイルクローズが「無言の出口」になっていないか。
   出ないことが正しいなら、その理由がコメントに書いてあるか。
2. 同じ経路を通る呼び出しの数が揃っているか。
   1 箇所で沈黙していたら、だいたい全部沈黙している
   （トーストは 8 箇所、入国要件は 5 か国だった）。
3. 定数表・対応表の網羅。片方に足してもう片方に足し忘れる形
   （entry_requirements に 7 か国を足したとき kCountrySupport に
   足し忘れた、が実例）。
4. 同じ処理が 2 か所以上にある箇所。既知の修正が全部に入っているか。
   とくに時刻・タイムゾーン・上限。
5. 「出る」ことをテストが固定しているか。
   「落ちない」テストは、出ないことも通す。
6. **状態が自動で進むか。** 状態の集合（`kStatuses` のような列挙）に対して、
   **そこへ入る経路が実装されているか**を 1 つずつ数える。
   実例（2026-08-16・利用者から報告）: 予定の状態に `進行中` があり、
   タイムラインの丸も `進行中` を描き分ける実装が入っていたのに、
   **自動で入る経路が無かった**。自動で入るのは `完了` だけで、
   開始時刻を過ぎても丸は空のまま。**落ちも警告も出ない。**
   `kConciergeEnabled` が「定義はあるのに誰も読んでいない」だった件と同型で、
   こちらは「状態はあるのに誰も書かない」。
   🔴 **足す側を直したら、受ける側も数える。** 上の件では
   「`未開始` の予定だけ完了にする」実装が残っており、そのままだと
   **一度 `進行中` になった予定は二度と完了しない**。対で直す。

出し方: 無言の出口は数が多い。全部を所見にせず、
「出ないと利用者が損をする」ものだけを所見にする。それ以外は末尾に
「正当な沈黙と判断したもの」として場所だけ列挙する。

見る観点:

2. フラグを true にした瞬間に何が壊れるか。

3. 上限の書き手と読み手のキーが一致しているか。

5. 429（上限）と 503（予算）が同じ文言にまとめられていないか。

6. 購入が成立したのにプランが反映されない経路が残っていないか

見る観点:
1. RLS 前提のクエリ。

7. 管理コンソール（`https://junros.coyoteandpowell.com/admin`）。
   **全利用者のデータに届く面なので、アプリと同じ重さで見る。**
   - 誰が入れるか（`toritavi_admin_members` の行・昇格の経路）
   - 未ログイン・非管理者で到達できる画面・API が無いか

   - 監査ログ（`toritavi_admin_audit_logs`）に何が残るか

### 認証済み分離プローブ（レーン 5 の実測部分）

**コードを読むだけでは、RLS が効いていることは分からない。**
匿名プローブが緑でも「ログイン済みの他人から見えるか」は何も見ていない。
2026-08-16 まで、この面は一度も測っていなかった。

🔴 **`set -a` を必ず付ける。** `~/.junros-probe.env` は `export` を含まない
素の代入なので、`source` しただけでは子プロセス（`bash tool/rls_probe.sh`）に
渡らない。**渡らないと「⚠️ 未実行」を出しつつ終了コード 0・末尾 🟢 で終わる。**

```
set -a; . ~/.junros-probe.env; set +a
bash tool/rls_probe.sh
```

> **2026-08-16 にここが間違っていた。** この節を書いた当日、
> 手順どおり（`set -a` 無し）に実行すると分離プローブが走らないまま
> 緑で終わることを実測した。`docs/subscription-setup.md` が
> `--dart-define` を案内していたのに `env.dart` は `.env` しか読まなかった
> （2026-08-02 発見）のと同じ型 —— **手順どおりでも機構に届かない。**
> 手順を書いたら、その手順で 1 度は実際に回すこと。

- テストアカウント **A（持ち主）と B（攻撃者役）** の 2 つが要る。
  資格情報は `~/.junros-probe.env`（**リポジトリの外**。中の `.env` は
  `pubspec.yaml` でアプリに同梱されるので、置くと配布物に焼き込まれる）
- 🔴 **A・B は使い捨てのアカウントに限る。** B のトークンで A の行に
  UPDATE / DELETE を試みる。RLS が正しければ 0 行だが、破れていれば
  実際に A のデータが変わる
- **⛔（検査不能）が 1 つでも残っていたら緑ではない。** A 側にデータを
  作ってから回し直す。「A が空だから 0 件」は何も証明しない
- 埋めるために A で作るもの: 旅程・予定・**スキャン画像**・連絡先（電話番号入り）・
  やることのチェック・設定の変更・フィードバック（添付付き）

### 匿名・ログイン済みの RPC 棚卸し（毎回・人が 1 本流す）

🔴 **2026-08-16 に、ここを誰も見ていなかったせいで実際に漏れていた。**
匿名キーだけで `toritavi_soft_deleted_scan_steps` が **HTTP 200 / 65 行**を返し、
`(owner_uid, step_id)` ＝ Storage のパス、つまり**全利用者のスキャン画像の所在**が
未ログインで列挙できた。削除関数 `toritavi_purge_orphan_trip_children` まで
匿名で叩けた。リポジトリの SQL には revoke が書いてあったのに、である。

`rls_probe.sh` は**読み取り専用と分かっている関数だけ**を実際に叩く。
副作用のある関数は叩けないので、**全関数の棚卸しは人が SQL Editor で行う**。

```sql
select p.proname, pg_get_function_identity_arguments(p.oid) as args,
       pg_get_function_result(p.oid) as returns,
       has_function_privilege('anon',          p.oid, 'EXECUTE') as anon_can,
       has_function_privilege('authenticated', p.oid, 'EXECUTE') as auth_can
  from pg_proc p join pg_namespace n on n.oid = p.pronamespace
 where n.nspname = 'public'
 order by anon_can desc, auth_can desc, p.proname;
```

- **`anon_can = true` が 1 つでもあれば revoke。** ただし `returns = trigger` は
  PostgREST から呼べないので対象外（`cascade_soft_delete_steps` 等）
- `auth_can = true` は「アプリが端末から呼ぶもの」だけに絞る。
  正解は `grep -rn "\.rpc(" lib/` の結果と一致すること（現在 `increment_ad_impression` の 1 本）
- 閉じ方は**両方書く**:
  ```sql
  revoke execute on function public.<名前>(<引数>) from anon, authenticated;
  ```

> ⚠️ **OpenAPI（`GET /rest/v1/` の `application/openapi+json`）で面を数える案は
> 使えない。** この本番はテーブル面も RPC 面も 0 件を返す。採用すると
> 「何を revoke しようが永久に 0 件 ✅」の空振りの緑になる（実測して不採用にした）。
