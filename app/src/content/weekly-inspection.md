# 週次検査（Fable 5 に検査させ、Opus が直す）

> **この文書が正本。** サーバ側 `src/content/weekly-inspection.md` はコピーで、
> 管理画面 `/admin/maintenance` のタブとして表示するためだけに置いてある。
> 直すときは必ずこちら。

## 週次検査（Fable）

**Fable は検査だけ。実行と修正は Opus。** 毎週 1 回、レーンを 1 つ選んで回す。
5 レーンあるので 5 週で一巡する。急ぐときは複数レーンを同じ週に回してよいが、
**1 セッション 1 レーン**にする（混ぜると読む資料が増えて精度が落ちる）。

### なぜこの形か

**「バグ」より「静かな不一致」で痛い目に遭ってきた。** 一般的なコードレビューの
軸をそのまま渡すと、既に 800 件超のテストが守っている範囲を再走査して終わる。
だから軸は**テストが構造的に見られない所**へ寄せてある。

**過去の外部監査は 9 件中そのまま正しかったのが 3 件だった。** 出力は「所見」で
あって「事実」ではない前提で、**検証しやすい形を強制する**のがこの手順の肝。
とくに所見 1 件ごとの「これが偽である条件」を必ず書かせること。これが無いと
Opus 側の検証コストが跳ね上がる。

### 回し方（Fable をどこで動かすか）

**A. Opus に「レーン 1 を回して」と言う（普段はこちら）**

Opus が指示文を Fable 5 のサブエージェントへ渡し、返ってきた所見をそのまま
受け取って真偽判定 → 修正まで一続きでやる。**人間のコピペを挟まない。**

独立性は保たれる。サブエージェントは**まっさらな文脈で指示文だけを受け取る**
ので、Opus の思い込みを引き継がない。

**B. 別セッションで自分で回す（出先・別マシン）**

1. **`~/Dev/toritavi_app` を作業ディレクトリにして新しいセッションを開く**
2. モデルを **Fable 5** に切り替える（アプリのモデル選択から）
3. 管理画面 `/admin/maintenance` →「週次検査」タブ → **共通ブロック**をコピーして貼る
4. 続けて**その週のレーンブロック**を貼る
5. 出た所見を Opus のセッションへ貼る

> 🔴 **claude.ai のチャットに貼っても動かない。** コードを読む必要があるので、
> **リポジトリを作業ディレクトリにした Claude Code のセッション**であること。
>
> **管理画面のタブは右端にある。** タブ列は横に溢れているので、
> 「スキーマ変更」「セキュリティ運用」より右へスクロールする。

A を使う場合も管理画面のコピーは要る。**指示文そのものの置き場**として——
何を検査させているかを後から読み返せる、2 台目の Mac からも同じものが使える、
指示文を書き換えたら差分が git に残る。

### 手順

1. **共通ブロック**を貼る（毎回同じ）
2. その週の**レーンブロック**を貼る
3. 返ってきた所見を Opus に渡す → 1 件ずつ真偽判定 → 真のものだけ着手
4. **偽が半分を超えたレーンは、直すのではなくそのレーンの指示を書き直す**

直す順序は必ず「**出ることを固定するテストを先に書く**」。「落ちない」テストは
出ないことも通してしまう。

### 共通ブロック（毎回これを先に貼る）

```
あなたは JUNROS（Flutter + Supabase の iOS 旅程アプリ）のコードを検査する。
検査だけを行う。

## 先に読むもの
- CLAUDE.md（とくに §5 判断の原則 / §6 既知の危険物 / §6-1 沈黙の検査項目）
- docs/ 配下の正本文書（service-spec / monetization-spec / feature-flags /
  travel-info-safety / data-privacy-spec）
- test/ のファイル名一覧（何が既に守られているかを把握するため）

## 禁止事項
1. コードを変更しない。パッチ・差分・修正案を書かない。
   直し方を決めるのは実装側の判断であり、監査が直し方まで書くと
   「もっともらしい修正」に引っ張られる。所見は「どこが・どういう入力で・
   どう壊れるか」まで。
2. テストが緑であることを、正しさの根拠にしない。
   このリポジトリでは実際に、テストが矛盾の誤った側を正解として固定していた。
3. 本番 DB に接続しない。SQL を実行しない。
4. リポジトリに定義が無い本番オブジェクト（increment_ocr_usage 等の DB 関数）
   について、コードだけを見て断定しない。該当したら
   「DB 側の確認が必要」と書く。
5. 推測を事実として書かない。推測なら「推測」と明記する。
6. 既存テストが既に守っている事柄を所見にしない。
   （守れていないと考えるなら、なぜ通ってしまうかを書く）

## 所見の書式（1 件ごとに必ずこの 7 項目）
- 分類 / 深刻度
- 場所: file:line
- 主張: 1 文。「〜が〜のとき〜になる」
- 壊れ方: 具体的な入力 → 実際に起きること（画面・DB・ログのどれか）
- 根拠: コードの引用。推測なら「推測」と明記
- これが偽である条件: 私が最初に確認すべき 1 点
- 既存テストの状態: 守られている / 通ってしまう / 該当なし

## 深刻度
- 致命: 写真・PII の流出、課金の嘘、上限が効かない、データ消失
- 高:   機能が黙って消えている、正本と実装の食い違いで利用者が騙される
- 中:   文書間の矛盾、いま動くが次の変更で壊れる形
- 低:   表記ゆれ、読みにくさ

## 進め方
所見が出なくなるまで探す。1 周して終わりにせず、
**2 周連続で新しい所見がゼロ**になったら「枯れた」と書いて終了する。
件数の目標は置かない（目標を置くと尻尾を取りこぼす）。

最後に「見ていない範囲」を明記すること。
```

### レーン 1 — 沈黙（出ないのに落ちない）

**最優先。** 実際に 3 件起きた形で、最も見つけにくく最も痛い。

```
レーン 1: 沈黙の検査。

## 探すもの
機能が消えても例外が出ない形。呼び出し側は実行したつもりで、画面には何も
起きず、テストも通る。

実際に起きたもの（校正用。同じ形が他にないか探す）:
- 削除の Undo トーストが 8 箇所すべて出ていなかった
  → Overlay.maybeOf が null を返し、黙って return していた
- 7 か国の入国要件が丸ごと無効
  → applies_to が空＝フェイルクローズで対象外扱いになっていた
- OCR 上限が毎日 9 時間効いていなかった
  → 複製した SQL 関数に、既知の JST 修正が入っていなかった

## 具体的に見る観点
1. 早期 return・空 catch・?? のフォールバック・orElse・maybeOf・
   フェイルクローズが「無言の出口」になっていないか。
   出ないことが正しいなら、その理由がコメントに書いてあるか。
2. 同じ経路を通る呼び出しの数が揃っているか。
   1 箇所で沈黙していたら、だいたい全部沈黙している
   （トーストは 8 箇所、入国要件は 5 か国だった）。
3. 定数表・対応表の網羅。
   片方に足してもう片方に足し忘れる形（entry_requirements に 7 か国を
   足したとき kCountrySupport に足し忘れた、が実例）。
4. 同じ処理が 2 か所以上にある箇所。
   既知の修正が全部に入っているか。とくに時刻・タイムゾーン・上限。
5. 「出る」ことをテストが固定しているか。
   「落ちない」テストは、出ないことも通す。

## 出し方
無言の出口は数が多い。全部を所見にせず、
**「出ないと利用者が損をする」ものだけ**を所見にする。
それ以外は末尾に「正当な沈黙と判断したもの」として場所だけ列挙する。
```

### レーン 2 — 整合性（言っていることと、やっていること）

```
レーン 2: 整合性の検査。

## 探すもの
文書とコード、文書と文書、内部値と表示名の食い違い。

## 具体的に見る観点
1. 正本文書 ↔ コード。
   数字（上限・価格・保持日数）、フラグ名と既定値、カテゴリ名、状態名。
   **数字はコードが正しいとは限らない。** どちらが正本かを文書側の
   宣言（「ここが正本」）で判定する。
2. 文書 ↔ 文書。
   同じ事項を 2 か所以上が定義していないか。定義しているなら食い違って
   いないか。2026-08-02 に、フェーズ定義が 5 文書で割れていたのを直した
   ばかりで、同じ構造が他にも残っている可能性がある。
3. 内部値 ↔ 表示名。
   - 内部コード名 `toritavi` が利用者の目に触れていないか（対ユーザー名は
     JUNROS）
   - Step.category の生値（飛行機・宿泊）が画面に出ていないか
     （表示は categoryLabel() を通した フライト・ホテル）
   - 旅程の状態の内部値「完了」が画面に出ていないか（表示は「終了」）
   同種の変換が他にもあれば、その出口が 1 か所に集約されているかを見る。
4. 公開文書 ↔ 実装。
   未稼働の機能を公開文書（App Store 掲載文・プロモ文言・プライバシー）に
   書いていないか。逆に、実装済みで開く予定のものを「言ってはいけない」
   一覧に残していないか。
```

### レーン 3 — 課金と上限（開ける直前にしか安く直せない）

```
レーン 3: 課金と上限の検査。

## なぜ今か
kSubscriptionEnabled はまだ false だが、初回リリースで開けると決まっている。
**開けた瞬間に初めて通る経路**なので、テストも運用実績も無い。
開ける前にしか安く直せない。

## 具体的に見る観点
1. フラグ false のとき、購入導線が完全に閉じているか。
   画面・API・文言・残数表示のどこかに「買える」と読める出口が
   残っていないか。
2. **フラグを true にした瞬間に何が壊れるか。**
   false 前提で書かれた分岐・文言・既定値を探す。
   「false のときだけ正しい」コードは、開けた日に嘘になる。
3. 上限の書き手と読み手のキーが一致しているか。
   日次/月次の境界、タイムゾーン（JST か UTC か）、リセット時刻。
   書き込み側（DB 関数）と読み取り側（サーバのガード）で基準がずれると、
   ずれた時間帯だけ上限が効かない。
   ※ DB 関数の定義はリポジトリに無い。該当したら
     「DB 側の確認が必要」と書く。
4. 端末に上限の数字を持っていないか。
   購入画面の件数はサーバの値から取る決まり。端末に書くと env を変えた
   ときに購入画面だけが嘘をつき、それは課金の約束になる。
5. 429（上限）と 503（予算）が同じ文言にまとめられていないか。
   原因も復旧時間も違う。
6. 購入が成立したのにプランが反映されない経路が残っていないか
   （webhook の宛先・リトライ・重複）。
```

### レーン 4 — 写真と PII の全経路

```
レーン 4: 写真（スキャン画像）と PII の経路検査。

## なぜ最優先の価値か
搭乗券・パスポート・予約票が写る。流出防止がこのアプリの第一原則。

## 具体的に見る観点
**撮影 → 圧縮 → 送信 → 保存 → キャッシュ → 表示 → 共有 → 削除**
の全経路を 1 本ずつ追い、各段で「残るもの」を挙げる。

1. 一時ファイル。image_picker / file_picker / PDF プレビューが作る中間物が
   後始末されているか。失敗経路（例外・キャンセル）でも消えるか。
2. ログ・エラー文・トースト。
   ファイル名・URL・確認番号・メールアドレス・氏名が出ていないか。
   例外をそのまま画面やログに流していないか。
3. 開発用ハーネス（lib/dev/）。
   実データが混ざっていないか。外部公開素材に使える状態か。
4. 削除の実効性。
   予定・旅程・アカウントを消したとき、Storage の実体・キャッシュ・
   端末内の残骸まで消えるか。「消したつもり」が残っていないか。
5. 送信先。
   画像・本文が渡る先が固定されているか。設定や入力で差し替わらないか。
```
